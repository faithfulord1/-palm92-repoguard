## Direct observations

- A single invoice task ran for six model steps and ended
  `max_steps_reached` with no touched files, no test result, and no proposal.
- The model emitted **valid JSON** in all six `model_action` entries.
- Ordered actions:
  1. read `invoice.py`;
  2. read `tests/test_invoice.py`;
  3. read `pricing.py`;
  4. read `invoice.py` again;
  5. read `invoice.py` again;
  6. read `invoice.py` again.
- No `invalid_model_json` events. Each read returned a normal tool
  observation. No `write` or `test` action occurred.
- This diagnoses a **repeated-read / no-progress loop** in the observed invoice
  diagnostic, *not* a JSON-format error. Other medium-v001 tasks lack full
  audit logs, so their individual failure mechanisms remain undetermined.

## Follow-up change

The v0.9 development branch now tracks unchanged source reads, exposes
`already_read_paths` and explicit action-progression guidance, returns
`repeated_read_blocked` on duplicate reads, and invalidates the read cache
for any file an approved write actually changes. A scripted regression test
proves the duplicate is blocked without preventing a subsequent verified
repair. These are engineering changes, not a guarantee of Gemma's behavior.
