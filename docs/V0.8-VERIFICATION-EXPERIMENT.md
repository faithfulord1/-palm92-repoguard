# RepoGuard v0.8 Verification Experiment

## Baseline evidence

The v0.7 Lite baseline is frozen under `artifacts/v0.7-lite/`.

Observed baseline:

- tasks: 4
- fixed: 1
- fix rate: 25%
- test pass rate: 50%
- average steps: 11.75
- average latency: 193.2126 seconds
- human intervention rate: 0%
- proposals created: 5
- proposals approved: 5
- proposals rejected: 0

## Failure pattern

The task-level evidence showed:

- `logic-divide-001`: no proposal, no passing tests, max steps reached
- `string-normalize-001`: one approved edit, tests still failed, max steps reached
- `boundary-clamp-001`: tests passed but the agent still reached the step limit
- `boolean-access-001`: tests passed and the agent correctly finished

## v0.8 change

v0.8 changes one primary behavior:

> After an auto-approved low-risk write in an isolated benchmark repository, RepoGuard immediately runs the test suite.

If tests pass, RepoGuard records verified evidence and stops with `status=fixed`.

If tests fail, the failure output is included in the observation returned to the model so the next action can revise the patch.

The system prompt also explicitly asks the model to avoid unnecessary loops and to revise based on failing tests.

## Controlled experiment

The experiment deliberately keeps the following constant:

- model: `google/gemma-4-E4B-it`
- quantization: 4-bit
- task pack: `benchmarks/v0.6_tasks.json`
- max steps: 12
- approval policy: `auto_low_risk`
- isolated benchmark repositories

Experiment ID:

`verification-v001`

## Hypothesis

Automatic post-write verification should:

1. correctly classify test-passing patches as fixed,
2. reduce unnecessary steps after a successful patch,
3. expose failed patch evidence earlier to the model,
4. improve fix rate and/or average step count without weakening governance.
