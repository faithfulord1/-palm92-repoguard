# RepoGuard v0.9: medium multi-file experiments

Status: **Prepared, not executed.** Branch `v0.9-hard-benchmarks`.
The historical v0.7 Lite and v0.8 files are preserved without edits.

## Objective

Explore whether RepoGuard's v0.8 post-write testing and bounded loop can repair
three small but more realistic **medium** Python defects spanning module
boundaries: per-line Decimal rounding, slice pagination, and hierarchical access
checks. This is *not* a general performance benchmark.

## Controls and limitations

- Model: `google/gemma-4-E4B-it`, 4-bit, T4-class GPU where available.
- Task pack: `benchmarks/v0.9_tasks.json` (3 authored tasks, public tests).
- Maximum model steps: 12, isolated repo copies, auto-approval only of normal-risk
  edits inside those isolated benchmark copies.
- Compare v0.9 repeats **on the same v0.9 task pack**, not aggregate success
  percentages against the four easy v0.7/v0.8 tasks.
- Public test visibility and a very small authored task count limit conclusions.
- Verify the actual JSONL and test logs and distinguish claimed `fixed` status
  from truly verified post-write passing tests. No real repositories or production
  services should receive autonomous changes.

## Before spending GPU time

1. From repo root: `python -m pip install -e '.[gemma,dev]'`.
2. `python -m pytest -q` to check the RepoGuard regression suite.
3. `python scripts/check_v0_9_fixtures.py` to confirm the three defects are
   demonstrable (each fixture's pytest run must fail for the intended reason).
4. Confirm `torch.cuda.is_available()` is True.

## Run

`python scripts/run_v0_9_benchmark.py --experiment-id medium-v001`

For each independent repeat use a **new** ID, e.g. `medium-v002`, and preserve
the previous JSONL/summary. Inspect each task's actions, changed files,
verification test results, and any reported failure. Do not publish a v0.9
result before the run finishes and all files are saved outside ephemeral Colab.

## Next engineering gates

Investigate failures without modifying historical evidence. Later, introduce
a *separate* unseen held-out task set, enforce stricter change authorization
beyond benchmark copies, and run repeated seeds/settings before broader claims.
